# Redmine Kanban add-worktime

# Cross-tab・Time Entry整合性強化 変更仕様書

## 1. 目的

`redmine_kanban` の `add-worktime` ブランチに実装したWorktime機能について、最新レビューで残存したデータ整合性・複数タブ競合・iframe送信経路・Canvas操作上の問題を解消する。

本変更の最優先事項は次の2点とする。

```text
作業時間を失わない
+
同じ作業時間を二重登録しない
```

UI拡張よりTimerSessionの整合性を優先する。

# 3. 既存判断の扱い

## D-001 Gantt Storage Protocol

維持する。

```text
TimerSession version = 4
redmine_canvas_gantt_timer_*
instanceKey + userId scope
```

Kanban独自namespaceやgeneric namespaceへの移行は今回行わない。

---

## D-002 Lock fallback

従来判断を変更する。

旧判断:

```text
Web Locks
↓
localStorage lease
```

新判断:

```text
Web Locks
↓
IndexedDB lock
↓
localStorage lease
↓
すべて失敗
→ fail-closed
```

Canvas Ganttで既に利用している排他方式と同等の実装を採用する。

理由:

```text
1 Redmine instance
×
1 user
=
active / pending TimerSession 最大1
```

というInvariantをGantt/Kanban/複数タブ全体で可能な限り同じ方式で保証するため。

具体的なIndexedDB名・schema・lock取得方式は、実装時点のGantt `add-worktime` の最新実装を確認して合わせる。

---

# 6. Startup Recovery

Worktime初期化時にTimerSessionを確認する。

## 6.1 recordingAttemptなし

## 6.2 同一tab owner + editing

```text

```

は、

```text

```

```text

↓
```

# 10. Time Entry Submit Pipeline

Time Entry送信経路を1本に統一する。

対象:

```text
Kanban Footer Save
iframe内Enter
iframe native submit
その他form submit
```

すべて同一pipelineを通す。

---

# 11. Submit pipelineの順序

正式な処理順序を次とする。

```text
ユーザーsubmit
↓
single-flight取得
↓
TimerSession確認
↓
editing → submitting
↓
Storage mutation完了
↓
mutation成功確認
↓
Dialogがまだ有効か確認
↓
Redmine native form submit
```

Storage mutation成功前にRedmine formを送信してはならない。

---

# 12. Native Submit Interception

Worktime起点のTime Entry iframeでは、iframe documentの`submit` eventを捕捉する。

native submitを検出した場合:

```text
preventDefault
↓
Worktime submit pipeline
```

とする。

TimerSession reservation完了後の実際のnative submitについてのみ、内部bypassを利用して送信を許可する。

これによりEnter送信とFooter送信の挙動を一致させる。

---

# 13. Submit single-flight

送信準備中または送信中に、

```text
Save連打
Enter連打
Footer + Enter
```

が発生してもRedmine POSTを複数回発行してはならない。

submit preparationを含めsingle-flightとする。

---

# 14. Submit準備中のclose

TimerSessionを`submitting`へ変更する非同期処理中にDialogが閉じられた場合も、安全側へ倒す。

## Storageがまだediting

```text
close
↓
cancel recording
↓
pending保持
```

Redmine submitは行わない。

## Storageがsubmittingになった後

```text
close
↓
unknown
```

とする。

Dialog close後に遅延してRedmine formを送信してはならない。

---

# 15. Validation Error

Redmineがvalidation errorを返した場合、

```text
submitting
↓
editing
```

へのStorage変更を完了させてからUIを編集可能状態へ戻す。

正式順序:

```text
Redmine validation error確認
↓
markValidationError
↓
Storage mutation await
↓
editing確認
↓
Save操作再開
```

callbackをfire-and-forgetにしてはならない。

---

# 16. Validation状態更新失敗

Storage lock/storage error等により、

```text
submitting → editing
```

へ戻せない場合、UIだけをeditingとして再開してはならない。

以下とする。

```text
Timer state同期失敗を表示
↓
再submit禁止
↓
TimerSession同期を再試行
```

安全性を優先し、canonical stateとUI stateを分離させない。

---

# 17. Time Entry Success

Redmine登録成功が確認された場合、

```text
submitting
↓
complete
↓
TimerSession削除
```

とする。

TimerSession削除処理も可能な限り完了をawaitする。

登録成功後のTimer cleanupに一時的なlock競合が起きた場合は、Time Entryを再入力可能状態へ戻してはならない。

登録済みであることを保持し、cleanupを再試行する。

---

# 18. Time Entry Unknown

次の場合はunknownとする。

```text
submit後のiframeアクセス失敗
submit中のDialog close
submit中のowner tab reload
結果判定不能なnavigation
```

結果が判定できない場合にTimerSessionを削除してはならない。

# 25. Lock Strategy

Kanban側の排他方式をGanttと同等へ合わせる。

優先順位:

```text
1. Web Locks
2. IndexedDB
3. localStorage lease
```

最後まで取得できない場合:

```text
mutationしない
```

fail-openは禁止する。

---

# 26. localStorage lease

localStorage fallbackは最終fallbackとしてのみ使用する。

以下を維持する。

```text
owner確認
expiration
read-back ownership確認
自owner lockのみrelease
```

lease取得失敗時にmutationを実行してはならない。

# 45. 最終判断

本変更では機能追加を増やさず、Worktimeの状態整合性を完成させる。

特に、

```text
他tabだから自動Recoveryする
```

という考え方を禁止する。

正しくは、

```text
自分のtab
→ 自動Recovery可能

他tab
→ 状態維持

他tabが失われたことをユーザーが明示
→ 安全なRecovery
```

とする。

またTime Entryについては、

```text
UIボタン
native form
Enter
```

を別々の送信方式として扱わない。

すべて、

```text
TimerSession確定
↓
Redmine submit
```

という1つのtransaction boundaryを通す。

この2点をWorktime機能の最終的な整合性Contractとする。
